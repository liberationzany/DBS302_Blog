## 1. Introduction: Why Containers Matter

Every developer has heard the phrase, "It works on my machine." Containers exist to end that conversation. By packaging the app with its dependencies and runtime, Docker makes software behave the same way across laptops, servers, and cloud platforms.

This report follows the exact learning path from first principles (SDLC, deployment, CI/CD) to hands-on Docker labs (build, run, tag, push). It is structured as a timeline, with each date reflecting a milestone in the course.

## 3. March 5: First Look at Docker

Docker is a platform that lets you build, package, and run applications inside containers. A container includes the app and everything it needs to run (libraries, dependencies, configs), which guarantees consistent behavior.

**Why Docker matters**

1. Consistency across environments
2. Easy deployment
3. Dependency management
4. Isolation between apps
5. Efficient resource usage
6. Simplified development and testing

**CI/CD basics**

- **CI (Continuous Integration):** automatically integrates and tests code changes.
- **CD (Continuous Delivery / Deployment):** automatically delivers or deploys builds.

### 3.1 Docker architecture in six pieces

- **Docker Client:** where commands are issued.
- **Docker Host:** the system running Docker.
- **Docker Engine (Daemon):** builds and runs containers.
- **Docker Images:** read-only templates.
- **Docker Containers:** running instances of images.
- **Docker Registry:** storage for images (for example, Docker Hub).

## 4. March 9: Traditional Deployment

Before containers, deployments were manual and slow:

1. Prepare the server
2. Install the OS
3. Install dependencies
4. Copy app code
5. Configure settings
6. Start the app

This approach was error-prone, difficult to scale, and created version conflicts between apps.

## 5. March 16: SDLC and CI/CD

**SDLC models**

- **Waterfall:** sequential phases, rigid for change.
- **Agile:** iterative development with continuous feedback.
- **Spiral:** combines design and risk analysis.
- **V-Model:** testing paired with each development phase.

**SDLC vs CI/CD**

| SDLC | CI/CD |
| --- | --- |
| Overall software development process | Automation of build, test, deploy |
| Planning, design, development, maintenance | Integration and delivery focus |
| Methodology/framework | DevOps practice |

## 6. March 19: Linux Command Practice

```text
# How many directories are present?
tree .

# Create empty files inside a directory
touch empty_file.txt

# Create a file with content
nano contents_file.txt
# (write content, then Ctrl+X, Y, Enter)

# Create an empty directory
mkdir empty_dir

# Create a directory hierarchy
mkdir -p asia/india/bangalore

# Copy a file to a target directory
cp bangalore.txt /home/thor/asia/india

# Copy a source directory recursively
cp -r /home/thor/asia/india/bangalore /home

# Remove a target file
rm /home/thor/asia/bangalore.txt

# Remove a directory and all its contents
rm -rf /home/thor/asia/india/bangalore
```

Flags used: `-p` creates parent directories, and `-r` enables recursive copy or delete.

## 7. March 23: Containers, Images, and Cloud

### 7.1 Container vs. Virtual Machine

| Feature | Virtual Machine | Docker Container |
| --- | --- | --- |
| Boot time | Minutes | Seconds |
| Storage | Heavy | Light |
| OS | Full OS per VM | Shares host kernel |
| Size | Gigabytes | Megabytes |

Containers are faster because they share the host OS kernel instead of running their own.

### 7.2 Container vs. Image

| Feature | Container | Image |
| --- | --- | --- |
| Definition | Running instance | Blueprint/template |
| State | Active | Static |
| Modifiable | Yes | No |
| Creation | From image | Built with Dockerfile |

### 7.3 Docker editions

| Feature | Community Edition | Enterprise Edition |
| --- | --- | --- |
| Cost | Free | Paid |
| Users | Students, small projects | Enterprises |
| Support | Community | Official |
| Updates | Frequent | Stable releases |

### 7.4 Cloud service models

- **IaaS:** rent virtual hardware (for example, AWS EC2).
- **PaaS:** deploy apps without managing servers (for example, GCP App Engine).
- **SaaS:** use software as a service (for example, Gmail).

## 9. March 30: Inspecting Containers and Jenkins

```text
# List running containers
docker ps

# Run a command inside a running container
docker exec <container-id> cat /etc/*

# Run an alpine container in a loop printing the date
docker run alpine sh -c "while true; do date; done"
```

**Container exit codes**

| Exit Code | Signal | Cause |
| --- | --- | --- |
| 130 | SIGINT | Stopped using Ctrl+C |
| 137 | SIGKILL (9) | Force killed via docker kill or OOM |
| 143 | SIGTERM (15) | Graceful stop via docker stop |

## 10. April 16: Jenkins, Networking, and Persistence

**Jenkins basics**

Jenkins is an automation server that builds, tests, and delivers software. It does not deploy by itself, but orchestrates the pipeline that leads to deployment.

**Networking terms**

- **MAC address:** hardware identity of a network interface.
- **Gateway:** entry/exit point between networks.

**Launching Jenkins**

```text
docker run -p 8080:8080 -p 50000:50000 jenkins/jenkins:latest
```

The `-p 8080:8080` flag maps external port 8080 to container port 8080.

**Persistence**

Docker volumes keep data even if the container is deleted. A local directory for Jenkins data can preserve build history and configuration across restarts.

## 12. April 23: First Flask Docker Image

**Workflow**

Create app -> write Dockerfile -> build image -> run container -> tag -> push

**Flask app**

```python
import os
from flask import Flask
app = Flask(__name__)

@app.route("/")
def main():
    return "Welcome!"

@app.route('/how are you')
def hello():
    return 'I am good, how about you?'

if __name__ == "__main__":
    app.run(host="0.0.0.0", port=8080)
```

Run locally:

```text
python3 app.py
```

**Dockerfile**

```Dockerfile
FROM python:3.10-slim

WORKDIR /app

COPY . .

RUN pip install flask

EXPOSE 8080

CMD ["python", "app.py"]
```

**Build and run**

```text
# Build the image and tag it as flaskapp
docker build -t flaskapp .

# Run the container, mapping port 8080 to the host
docker run -p 8080:8080 flaskapp
```

**Tag and push to Docker Hub**

```text
# Build with a username/repo tag
docker build . -t sevenkels/flaskapp

# Run from the new tag to verify it works
docker run -p 8080:8080 sevenkels/flaskapp

# Push to Docker Hub
docker push sevenkels/flaskapp
```

## 13. April 26: KodeKloud Lab and Image Optimization

**Original Dockerfile**

```Dockerfile
FROM python:3.6

RUN pip install flask

COPY . /opt/

EXPOSE 8080

WORKDIR /opt

ENTRYPOINT ["python", "app.py"]
```

**Build and run**

```text
docker build -t webapp-color .
docker run -p 8282:8080 webapp-color
```

**Optimization lesson**

Switching from `python:3.6` to `python:3.6-alpine` reduced image size dramatically.

| Image | Tag | Size |
| --- | --- | --- |
| webapp-color | latest (python:3.6) | 913 MB |
| webapp-color | lite (python:3.6-alpine) | 51.9 MB |

**Inspect base image OS**

```text
docker run -it python:3.6 cat /etc/os-release
```

## 14. April 27: The Universal 5-Step Dockerfile Skeleton

The common pattern across all labs:

`FROM -> WORKDIR -> COPY -> RUN -> CMD`

**Step 1: FROM**

```Dockerfile
FROM python:3.10-slim
```

**Step 2: WORKDIR**

```Dockerfile
WORKDIR /app
```

**Step 3: COPY**

```Dockerfile
COPY . .
```

**Step 4: RUN**

```Dockerfile
RUN pip install flask
```

**Step 5: EXPOSE + CMD**

```Dockerfile
EXPOSE 8080
CMD ["python", "app.py"]
```

**Lab challenge: Node.js Dockerfile**

```Dockerfile
# 1. Base image
FROM node:18-alpine

# 2. Set working directory
WORKDIR /app

# 3. Copy files
COPY package*.json ./
RUN npm install
COPY . .

# 4. Expose port
EXPOSE 8080

# 5. Run the app
CMD ["node", "server.js"]
```

Copying `package*.json` first allows Docker to cache `npm install` and rebuild faster when source files change.

## 15. Key Takeaways

| Principle | Why it matters |
| --- | --- |
| Containers share the host kernel | This makes them fast and lightweight |
| Images are blueprints, containers are running instances | Confusing the two breaks the mental model |
| The 5-step skeleton covers most images | Dockerfile authoring becomes routine |
| Base image choice dominates size | Alpine cuts size dramatically |
| Volumes give persistence | Containers can be disposable without losing data |
| Port mapping is essential | Without it, services are unreachable |
| Layer caching rewards ordering | Copy manifests first, then install |
| Tagging enables pushing | Username/repo links to Docker Hub |
