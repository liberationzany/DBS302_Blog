## 1. Introduction: Redis and the In-Memory Model

Redis is a key-value database built around speed. It keeps data in RAM, which makes most operations extremely fast. This design makes Redis ideal for caching, real-time analytics, sessions, and many other low-latency workloads.

<!-- truncate -->

## 2. What Is a Key-Value Database?

A key-value database stores data as pairs of a unique key and its associated value, similar to a Python dictionary or a Java HashMap.

**Analogy: gym locker system**

Each locker has a unique number (the key) and whatever you place inside is the value. If you know the locker number, you retrieve your belongings in $O(1)$ time without searching through every locker.

## 3. Redis Architecture

Redis uses a client-server model over TCP/IP and relies on three core architectural pillars:

- **In-memory storage:** Data lives in RAM, avoiding disk I/O.
- **Non-blocking I/O (multiplexing):** Uses an event loop to handle many connections efficiently.
- **Single-threaded command execution:** Avoids context switching and locking overhead.

## 4. Advantages of Redis

| Advantage | Why it matters | Example |
| --- | --- | --- |
| Blazing fast | In-memory operations, many are $O(1)$ | 1,000,000+ ops/sec on one machine |
| Simple model | No schemas or joins | Store session data without tables |
| Horizontally scalable | Redis Cluster shards across nodes | Add nodes as traffic grows |
| Flexible types | Rich data types beyond strings | Sorted sets for leaderboards |
| Atomic operations | Commands like INCR are atomic | Safe concurrent counters |
| TTL support | Keys can expire automatically | Expire sessions after 30 min |
| Pub/Sub built in | Event broadcasting | Real-time chat notifications |

## 5. Limitations of Redis

| Limitation | Explanation |
| --- | --- |
| Memory-bound | All data lives in RAM, which is expensive |
| No complex queries | No JOIN or GROUP BY; design for access patterns |
| Limited ACID | MULTI/EXEC is not a full SQL transaction |
| Key-based lookup | Scanning all keys is $O(N)$ and risky |
| Persistence complexity | Requires configuration to prevent data loss |

## 7. Redis Fundamentals

### 7.1 Key naming conventions

Since all keys share the same namespace, use structured naming:

Pattern: `object-type:id:attribute`

Examples:

- `user:1001:profile`
- `product:sku:BTN500:details`
- `order:ORD2024001:status`
- `cache:homepage:trending`

Tip: Use colons consistently so you can safely scan related keys with `SCAN 0 MATCH user:*`.

### 7.2 Data types

#### Strings

Binary-safe values for text, numbers, JSON, or blobs (max 512 MB).

```text
SET username "Alice"
GET username
INCR counter
SETEX session:tok123 3600 "user:1001"
EXPIRE username 86400
```

**Example: rate limiting**

```text
SET ratelimit:user:1001:tweets 0
INCR ratelimit:user:1001:tweets
EXPIRE ratelimit:user:1001:tweets 10800
```

#### Lists

Ordered lists with push/pop from both ends.

```text
LPUSH tasks "send_email"
RPUSH tasks "generate_pdf"
LLEN tasks
LRANGE tasks 0 -1
LPOP tasks
BLPOP tasks 30
```

**Example: background queue**

```text
RPUSH jobs:image:resize "{photoId: 9876}"
BLPOP jobs:image:resize 30
```

#### Sets

Unordered collections of unique values.

```text
SADD followers:user:1001 "user:2001" "user:3001"
SMEMBERS followers:user:1001
SISMEMBER followers:user:1001 "user:2001"
SINTER tags:article:101 tags:article:102
SUNION tags:article:101 tags:article:102
SDIFF tags:article:101 tags:article:102
```

**Example: mutual connections**

```text
SINTER connections:alice connections:bob
```

#### Hashes

Field-value maps stored under one key.

```text
HSET user:1001 name "Alice Sharma" email "alice@example.com" age 28
HGET user:1001 name
HGETALL user:1001
HMGET user:1001 name email
HINCRBY user:1001 age 1
```

**Example: repository stats**

```text
HSET repo:torvalds/linux stars 170000 forks 49000 language "C"
```

#### Sorted Sets (ZSets)

Unique members with floating-point scores, always kept sorted.

```text
ZADD leaderboard 9500 "player:alice"
ZADD leaderboard 8200 "player:bob"
ZREVRANGE leaderboard 0 2 WITHSCORES
ZRANK leaderboard "player:alice"
ZINCRBY leaderboard 500 "player:alice"
ZRANGEBYSCORE leaderboard 8000 10000
```

**Example: top users leaderboard**

```text
ZREVRANGE reputations 0 99 WITHSCORES
```

## 8. Global Key Commands

```text
EXISTS user:1001
DEL user:1001
TYPE user:1001
RENAME user:1001 user:old:1001

EXPIRE user:1001 3600
TTL user:1001
PERSIST user:1001

SCAN 0 MATCH user:* COUNT 100
```

Warning: never run `KEYS *` in production. It is $O(N)$ and blocks all other operations. Use `SCAN` instead.

## 10. Advanced Redis Data Structures

### 10.1 Bitmaps

Bitmaps treat a Redis string as a bit array for space-efficient boolean flags.

```text
SETBIT logins:2024-01-15 1001 1
GETBIT logins:2024-01-15 1001
BITCOUNT logins:2024-01-15
BITOP AND active_both logins:2024-01-15 logins:2024-01-16
```

Memory comparison (10M users):

- Redis Set (exact): ~100 MB
- Bitmap: ~1.25 MB

### 10.2 HyperLogLog

Estimates unique counts with fixed memory (~12 KB).

```text
PFADD pageviews:homepage "192.168.1.1"
PFADD pageviews:homepage "10.0.0.25"
PFCOUNT pageviews:homepage
```

Typical accuracy is about 0.81% standard error.

### 10.3 Bloom Filters

Fast membership tests with a small false-positive rate.

```text
BF.RESERVE crawled_urls 0.001 10000000
BF.ADD crawled_urls "https://example.com/page1"
BF.EXISTS crawled_urls "https://example.com/page1"
BF.EXISTS crawled_urls "https://newsite.xyz/unknown"
```

### 10.4 Geospatial indexes

Store coordinates and run proximity queries.

```text
GEOADD drivers 89.6419 27.4712 "driver:D001"
GEOADD drivers 91.1006 26.1445 "driver:D002"
GEODIST drivers "driver:D001" "driver:D002" km
GEOSEARCH drivers FROMLONLAT 89.6419 27.4712 BYRADIUS 50 km ASC COUNT 5
```

## 11. Persistence and Durability

Redis keeps data in memory, so persistence matters for recovery.

### 11.1 RDB snapshots

RDB creates point-in-time snapshots using fork + copy-on-write.

```text
save 900 1
save 300 10
save 60 10000

BGSAVE
SAVE
LASTSAVE
```

| Feature | Detail |
| --- | --- |
| File format | Compact binary .rdb |
| Performance impact | Low; fork is nearly instant |
| Recovery time | Fast; loads one file |
| Data loss risk | Up to last save interval |
| Best for | Backups and warm cache restarts |

### 11.2 AOF logs

AOF logs every write and replays on restart.

```text
appendonly yes
appendfsync always
appendfsync everysec
appendfsync no
```

### 11.3 Hybrid strategies

| Strategy | Data loss risk | Restart speed | Use case |
| --- | --- | --- | --- |
| No persistence | Total loss | Instant | Pure cache |
| RDB only | Up to minutes | Fast | Tolerable loss |
| AOF only | &le; 1 second | Slower | High durability |
| RDB + AOF | &le; 1 second | Fast | Production default |

## 12. Clustering and High Availability

### 12.1 Replication (primary-replica)

```text
replicaof 192.168.1.100 6379
INFO replication
```

### 12.2 Redis Sentinel (automatic failover)

```text
sentinel monitor mymaster 192.168.1.100 6379 2
sentinel down-after-milliseconds mymaster 5000
sentinel failover-timeout mymaster 60000
redis-sentinel /etc/redis/sentinel.conf
```

### 12.3 Redis Cluster (horizontal scaling)

```text
cluster-enabled yes
cluster-config-file nodes.conf
cluster-node-timeout 5000

redis-cli --cluster create \
  192.168.1.101:6379 192.168.1.102:6379 192.168.1.103:6379 \
  192.168.1.104:6379 192.168.1.105:6379 192.168.1.106:6379 \
  --cluster-replicas 1
```

Hash slots:

- 16,384 total slots
- slot = CRC16(key) % 16384

Sentinel focuses on high availability, while Cluster handles both high availability and horizontal scaling.

## 14. Performance Optimization

### 14.1 Pipelining

Without pipelining, every command is a round-trip. Pipelining batches commands and reduces latency.

```python
pipe = r.pipeline()
for i in range(10000):
    pipe.set(f"key:{i}", f"value:{i}")
results = pipe.execute()
```

### 14.2 Transactions (MULTI/EXEC)

```text
MULTI
DECRBY user:1001:credits 100
INCRBY user:2001:credits 100
EXEC
```

### 14.3 Lua scripts for atomic operations

```text
EVAL "
  local balance = redis.call('GET', KEYS[1])
  if tonumber(balance) >= tonumber(ARGV[1]) then
    redis.call('DECRBY', KEYS[1], ARGV[1])
    return 1
  else
    return 0
  end
" 1 user:1001:credits 100
```

## 16. The Reactor Pattern in Redis

The Reactor Pattern lets a single-threaded process handle massive I/O concurrency efficiently.

**Key components**

1. Resources: sockets and file descriptors
2. Event demultiplexer: epoll, kqueue, select
3. Reactor: the main event loop
4. Handlers: logic that processes commands

**Why Redis uses it**

A thread-per-connection model wastes memory and CPU on context switching. Redis uses non-blocking I/O and a single event loop to keep latency low.

**Benefits**

- High throughput (100,000+ requests per second on a single core)
- No context switching overhead
- No locking contention

**Event loop workflow**

1. Client sockets register with the demultiplexer
2. The reactor waits for active sockets
3. The OS returns ready sockets
4. The reactor dispatches read handlers
5. Redis executes the command
6. The write handler returns the response

Note: Since Redis 6.0, I/O threading can help parsing and serialization, but command execution remains single-threaded for atomicity.

## 17. Big O Complexity Reference

| Operation | Complexity | Notes |
| --- | --- | --- |
| GET / SET (string) | $O(1)$ | Hash table lookup |
| LPUSH / RPUSH / LPOP / RPOP | $O(1)$ | List ends |
| LRANGE | $O(S+N)$ | S=start offset, N=elements returned |
| SADD / SISMEMBER | $O(1)$ | Hash set |
| SUNION / SINTER / SDIFF | $O(N)$ | N=elements in all sets |
| HSET / HGET | $O(1)$ | Hash table |
| HGETALL | $O(N)$ | N=fields |
| ZADD / ZSCORE / ZRANK | $O(log N)$ | Skip list |
| ZRANGE / ZRANGEBYSCORE | $O(log N + M)$ | M=elements returned |
| KEYS * | $O(N)$ | Blocks Redis |
| SCAN | $O(1)$ per call | $O(N)$ total, non-blocking |

## 18. Data Type Decision Guide

Choose a Redis type based on access patterns:

- String: single value or JSON blob
- Hash: object with multiple fields
- List: ordered sequence or queue
- Set: unique collection
- Sorted set: ranked or scored data
- Geo: location data
- TimeSeries: time-based data
- Bitmap: boolean flags for many IDs
- HyperLogLog: approximate unique counts
- Bloom filter: membership check only

## 19. Security Considerations

### 19.1 Authentication and ACLs

Legacy password (Redis < 6.0):

```text
requirepass YourStr0ngP@ssw0rd!
redis-cli -a YourStr0ngP@ssw0rd!
```

ACL (Redis 6.0+):

```text
ACL SETUSER alice on >alice_pass ~user:* +GET +HGET +HGETALL
ACL SETUSER bob on >bob_pass ~order:* +@read
ACL SETUSER default off
```

### 19.2 SSL/TLS

```text
port 0
tls-port 6380
tls-cert-file /etc/redis/redis.crt
tls-key-file /etc/redis/redis.key
```

### 19.3 Security best practices

1. Bind to specific interfaces, never 0.0.0.0
2. Enable protected mode
3. Disable dangerous commands (for example, rename-command FLUSHDB "")
4. Run as non-root with a dedicated redis user
5. Set maxmemory to avoid OOM
6. Firewall port 6379
7. Use strong passwords and ACLs
8. Monitor ACL logs

Security incident reminder: In 2016, thousands of exposed Redis instances were compromised because they had no authentication and open ports. Always firewall Redis and use ACLs.

## 21. Key Principles Summary

| Principle | Rule |
| --- | --- |
| Key naming | Use type:id:field with colons |
| Searching keys | Use SCAN, never KEYS * |
| TTL | Always set TTL on cache keys |
| Persistence | Use RDB + AOF hybrid in production |
| HA | Minimum 3 Sentinels for failover |
| Scaling | Redis Cluster for data beyond single-node RAM |
| Security | Bind to localhost + firewall + ACL |
| Performance | Pipeline commands to reduce round-trips |
| Memory | Use hashes for small objects |
| Anti-pattern | Never KEYS *, never store huge values |
